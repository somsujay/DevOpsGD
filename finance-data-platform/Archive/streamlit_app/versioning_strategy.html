Key Principle

Core Rule
One script per layer per domain per release for initial table creation. All related tables within a medallion layer are grouped into a single versioned script. Subsequent changes (ALTERs, new tables) in later releases get individual scripts per change.

Version Format

V<release>.<domain_id>.<layer><sequence>__<description>.sql
SegmentPurposeRange
ReleaseDeployment wave / sprint1–999
Domain IDOwning domain (see registry)00–99
Layer + SequenceMedallion layer prefix + script order1xx=raw, 2xx=clean, 3xx=conformed

Layer Prefix Convention

RangeLayerPurpose
100–199RawRaw ingestion, staging tables
200–299CleanCleansed dimensions, SCD tables
300–399ConformedFacts, aggregates, business views

This guarantees raw objects are created before clean references them, and clean before conformed — within every domain.

Rule
Initial creation = bundled. Changes after release 1 = one script per change (never bundle unrelated ALTERs).

Rules

Naming Conventions

  • Use lowercase with underscores in descriptions
  • Initial creation: V1.050.100__create_raw_tables.sql
  • ALTER scripts: V2.050.100__add_<column>_to_<table>.sql
  • New table additions: V2.050.101__create_<table_name>.sql

Version Number Rules

  1. Never reuse a version number — even if the script failed and was removed
  2. Never insert a version below the current max — schemachange will skip it
  3. Always increment the sequence within your domain and layer
  4. Increment the release at sprint/deployment boundaries
  5. Respect layer boundaries — raw (1xx), clean (2xx), conformed (3xx)

Anti-Patterns

AvoidWhyDo Instead
Inserting versions below current maxSchemachange skips themUse next available sequence
Multiple domains sharing a domain ID rangeCollisions in parallel devStrict domain ID ownership
Splitting initial tables into separate scriptsUnnecessary fragmentationBundle all tables per layer in release 1
Bundling unrelated ALTERs (release 2+)Hard to debug, no partial rollbackOne change per file for ALTERs
Using sequential integers (V1, V2, V3)No domain separation, conflictsUse 3-part versioning
Hardcoding database namesBreaks multi-environmentUse {{ database }} Jinja vars
Conformed scripts in 1xx rangeLayer ordering violatedUse 3xx for conformed
Dependent domain with lower IDRuns before dependency existsAssign higher domain ID

Onboarding a New Domain

  1. Determine the dependency tier (source, dependent, or aggregation)
  2. Pick the next available domain ID within that tier
  3. Update this document with the new domain entry
  4. Create the folder structure: raw/<domain>/, clean/<domain>/, conformed/<domain>/
  5. Create three initial scripts:
    • V<release>.<id>.100__create_raw_tables.sql
    • V<release>.<id>.200__create_clean_tables.sql
    • V<release>.<id>.300__create_conformed_tables.sql
  6. Add R__ scripts for repeatable objects (views, procedures)

Subdomains

Parent domains at multiples of 50 (050, 100, 150...) with subdomains using sequential IDs (051, 052, ..., 099) — supports up to 49 subdomains per parent.

Subdomain Rules

  1. Parent runs before child — domain 050 always executes before 051 and 052
  2. Cross-subdomain references are safe within the same parent tier
  3. Procedures go in R__ scripts per subdomain
  4. Adding a subdomain later requires no renumbering
# Example subdomain structure:
V1.050.100__create_raw_tables.sql          (ecomm - parent)
V1.051.100__create_raw_tables.sql          (ecomm_budget - subdomain)
V1.052.100__create_raw_tables.sql          (ecomm_actuals - subdomain)

# Release 2+ ALTERs stay scoped:
V2.050.100__add_channel_to_bookings.sql
V2.051.201__add_allocation_tier_to_budget.sql
